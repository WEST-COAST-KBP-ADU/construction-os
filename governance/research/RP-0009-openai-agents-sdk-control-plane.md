## Question

Can Construction OS introduce an OpenAI Agents SDK-backed reasoning plane as a
strictly bounded **candidate-artifact producer**, while keeping authorization and
all external effects outside the model runtime and on the canonical
Deedseal/KBP controlled-execution path?

This packet is a Research Gate output under DR-0005. It authorizes no code,
dependency, project, API key, model call, hosted tool, connector, deployment,
storage, retention configuration, visitor-facing AI, PII processing, customer
contact, property conclusion, or external effect.

## Existing platform boundary

The current repository boundary is controlling:

- `governance/BOUNDARIES.md` prohibits provider configuration, credentials,
  application code, production workflows, customer-facing messages, permit/code/
  zoning/buildability conclusions, and sensitive-data storage without an
  owner-approved task packet.
- `governance/office/STATE.md` at the pinned base permits only a read-only
  data-boundary architecture challenge in parallel. Runtime credentials, model
  calls, PII, canonical writes, and visitor-path AI remain closed.
- Construction OS is Product 2. Deedseal/KBP is the intended Product 1 control
  plane. The latter integration is a target architecture, not a claim that an
  implementation contract already exists.

## Candidate target architecture (non-binding)

```text
synthetic/domain input
  -> deterministic input schema + data classification
  -> reasoning adapter (server-only; initially no external tools)
  -> strict CandidateArtifact schema
  -> deterministic policy / evidence validator
  -> OwnerReview packet candidate
  -> Deedseal/KBP grant -> gate -> brokered effect -> signed run record
```

The model has no direct path to a CRM, email, calendar, permit system, payment,
GIS production adapter, browser, filesystem, customer record, or deployment
control plane. A model-generated tool call is rejected unless a separately
authorized application policy accepts the proposed intent and the Deedseal/KBP
control plane authorizes the specific effect.

## CandidateArtifact v0.1 — research contract only

The first experimental artifact should be generated from synthetic fixtures only
and contain no identity, address, APN, coordinates, contact detail, raw
transcript, credential, or undisclosed source payload.

```json
{
  "schema_version": "candidate-artifact-v0.1",
  "synthetic_case_id": "fixture-only",
  "purpose": "preconstruction_readiness_candidate",
  "facts": [
    {
      "statement": "string",
      "evidence_ref": "approved-fixture-or-source-ref",
      "status": "candidate | unknown | requires_official_source_verification"
    }
  ],
  "assumptions": ["string"],
  "unknowns": [
    {
      "question": "string",
      "reason": "missing_evidence | ambiguity | policy_gate"
    }
  ],
  "recommended_next_steps": [
    {
      "kind": "owner_review | request_official_source | refuse",
      "rationale": "string"
    }
  ],
  "effect_authorization": "none",
  "requires_owner_review": true
}
```

The schema above is not an implementation interface and does not license a
model call. It is the smallest testable boundary for a future decision record
and work order.

## Trust boundaries and invariants to decide

| Boundary | Required invariant |
| :-- | :-- |
| Browser / public site | No API key, no direct model call, no visitor PII to the reasoning plane, and no external effect. |
| Reasoning adapter | Server-side only; accepts the smallest classified input; emits candidate artifacts only; defaults to deny/refuse on schema or policy failure. |
| Tool layer | Initial runtime has no effectful tools. Any future tool is deterministic, narrowly typed, server-owned, separately authorized, and independently logged. |
| OwnerReview | Explicit owner decision is required before an action can become eligible for authorization. A model pause, score, or recommendation is not approval. |
| Deedseal/KBP | Sole intended canonical effect path: bounded grant, gate, brokered execution, signed record, and independent verification. Integration details remain unverified until a versioned contract is adopted. |
| Evidence / observability | Record only sanitized correlation IDs, policy result, schema version, model/runtime version, allowed tool identity, and final accept/refuse class. Do not store raw prompts, customer content, or secrets by default. |

## Threat model and controls to carry forward

| Threat | Required control |
| :-- | :-- |
| Prompt injection or untrusted source text changes authority | Treat all model input as untrusted; do not place instructions in retrieved/domain text; validate structured output independently; first slice has no tools. |
| Model requests an unintended external action | The application interprets a request as a candidate only; fail closed unless policy and Deedseal/KBP authorize an exact bounded action. |
| PII or secret disclosure | Synthetic fixtures only; strict allowlists; server-side secret handling; no raw prompt/log retention in SourceTrue. |
| False construction/GIS/legal conclusion | Required uncertainty wording and refusal states; OwnerReview; no client-facing decision path. |
| Model, SDK, schema, or tool drift | Pin versions in a future work order; introduce contract tests, regression fixtures, and explicit compatibility policy. |
| Cost or runaway loops | No live runtime in this packet. Future work must define budget, rate, concurrency, timeout, retry, and circuit-breaker policy before enabling calls. |
| Evidence overclaim | Keep provider telemetry distinct from Deedseal/KBP run records. A trace proves only the recorded SDK/model activity, not external authorization or construction correctness. |

## Assumptions

- A future versioned Deedseal/KBP authorization contract can be exposed to
  Construction OS without sharing mutable internal implementation.
- A candidate-only synthetic evaluation can prove the boundary before any
  customer workflow, PII, or external integration is opened.
- A server-side reasoning adapter can be introduced behind the existing
  Next.js/Vercel public surface without giving browser code provider credentials.
  This requires future architecture and deployment verification.

## Risks and unknowns

- No OpenAI project, model allowlist, quota/spend policy, rate limit, SDK
  version, service account policy, environment, deployment topology, or
  observability configuration is selected.
- Default API data handling described in official documentation does not satisfy
  Construction OS's minimal-retention policy by itself.
- The exact Deedseal/KBP interface, signer ownership, record format,
  availability characteristics, and failure-mode integration are not yet
  established in this repository.
- A workflow pause for approval must not be mistaken for business authorization.
- A future use of hosted tools, MCP, file search, web search, sandbox agents, or
  connectors expands the trust boundary and needs its own task packet and
  security review.
- SDK and platform documentation may change after the checked date.

5. current SDK version, license, supported runtime, and vulnerability posture;
6. Vercel/server secret-management, egress, regionality, incident response, and
   rollback constraints;
7. legal/privacy requirements for any future customer data or third-party
   source material.

## Synthesis

A serious AI-native Construction OS should place an SDK-backed reasoning plane
**inside** a server-owned, typed, policy-checked candidate-artifact boundary,
not in the browser and not on the effect path. The official SDK model is
compatible with this split because the server can own tools, state, and approval
decisions; the control requirement remains stricter than the SDK alone.

The next decision is not “turn on an AI chatbot.” It is whether to adopt the
candidate-only boundary above and commission a separate, owner-approved
implementation packet for a synthetic, tool-free, server-side evaluation.
That later packet must name the exact repository base, implementation role,
independent reviewer, input/output schema, data classification, credential
scope, secret destination, model selection rule, test matrix, rollback, and
explicitly forbidden effects.

No implementation, runtime credential, model call, deployment, or external
effect is authorized by this research packet.
